一、代码结构（映射任务书第二十六章目录建议）
------------------------------------------------------------------------
node/
├─ main.go            manager  CLI：fetch/check/publish/status 四个命令
├─ model/model.go     统一节点结构 + 7态状态机常量 + 节点指纹
├─ sources/sources.go 来源管理：并发获取、file://与http(s)://、失败隔离
├─ parser/parser.go   节点解析：ss/trojan/vmess/vless 四协议 + 格式检查
├─ dedup/dedup.go     去重：按指纹合并、记录多来源
├─ checker/checker.go 粗筛：TCP 连通性并发测试（16 并发，5s 超时）
├─ cache/cache.go     节点池：持久化、合并、状态机、过期清理
└─ publish/publish.go 发布：base64 订阅 + sing-box JSON 双格式 + 统计

节点统一数据结构（任务书第十一章）：ID(指纹)/名称/协议/地址/端口/
参数(含敏感字段)/来源列表/首次发现/最后更新/最后检测/最后成功/
状态/连续失败次数/延迟。

状态机（任务书第十三章）：
NEW → 粗筛成功 → AVAILABLE（延迟>=2000ms 为 DEGRADED）
粗筛失败 → FailCount+1（连续 3 次 → FAILED；不因一次失败剔除）
7 天未在来源出现 → EXPIRED；EXPIRED 持续 14 天 → REMOVED 出池
来源重新出现 → 复活为 NEW 重新观察

指纹（任务书第十二章）：sha256(协议|地址|端口|凭据|sni/pbk/sid/net/
path/host)，不使用节点名称。

三、过程中发现并修复的真实缺陷
------------------------------------------------------------------------
1. Windows 下 file:///E:/x 路径解析错误 → 修复盘符斜杠处理
2. reality 节点 public_key 非法导致 sing-box FATAL
   → 解析器增加 32 字节 base64url 校验 + 发布器跳过非法节点（双保险）
3. ws 节点 path 含非法 % 转义导致 sing-box FATAL
   → 解析器/发布器两侧增加 url.Parse 可解析性校验
（上述缺陷均由"sing-box check 发布产物"这一步抓出，
 说明发布前校验必须保留在流程里）

四、关键实测结论（对后续阶段有直接影响）
------------------------------------------------------------------------
1. TCP 粗筛可用的节点 ≠ 协议可用：
   用发布配置实测免费节点，urltest 选中的"AVAILABLE"节点出现
   502(dial 超时) 与 400(端口上应答的是 nginx，trojan 协议已死)。
   -> 任务书第十四章"粗筛≠真实可用、以客户端设备端实测为准"
      的设计被实测直接验证。
   -> 建议后续升级：管线粗筛从纯 TCP 升级为协议级探测
     （借鉴 V2RayAggregator 用 LiteSpeedTest 的做法），
      归入阶段 2 后续迭代或阶段 5。
2. 免费节点时效性极强：urltest 选中节点 5 分钟内死亡。
   -> 客户端"连接失败自动换节点"（任务书第十五章）必要性强。
3. 本机已运行 v2rayN(sing-box 核心)，端口 7890 测试期间曾发生
   残留进程冲突 —— 客户端开发时需处理端口占用与残留进程检测。

九、追加迭代（2026-09-12 晚）：协议级深度检测 + 来源扩充 + 部署包
------------------------------------------------------------------------
1. [新增] 协议级深度检测（checker.Deep，解决"TCP 活着协议死了"）：
   原理：按批（默认 32 个）生成多入站/多出站 sing-box 配置
   （入站 i 固定路由到出站 i），启动单个核心进程并发验证整批，
   真实完成协议握手 + 外网 HTTP 请求。约 12s/批，611 节点约 3 分钟。
   首次全量实测结果：611 个节点，协议级可用仅 1 个
   （对比 TCP 粗筛的 138 个"可用"——粗筛虚高约 100 倍），
   另有 137 个判定较差（连通但延迟>=2s）。
   配置：data/pipeline.json（核心路径/开关/批大小/起始端口）。

2. [新增] 来源扩充（11 个默认来源，均已逐一预检或实测）：
   新增 roosterkid openproxylist(jsDelivr)、Pawdroid Free-servers
   (jsDelivr)、ermaozi get_subscribe(raw)、mahdibland Eternity(raw)、
   Epodonios ss/trojan(raw，整文件 base64 解析实测通过)。
   注意：来源可达性随时间波动（ermaozi 的 jsDelivr 与 raw 一个不通
   一个通），失败隔离机制持续兜底。

3. [新增] GitHub Actions 部署包：
   .github/workflows/node-pipeline.yml —— 每 2 小时自动构建管线、
   下载 sing-box、运行 fetch（含深度检测）、提交发布产物；
   产物经 jsDelivr 即成镜像通道
   （cdn.jsdelivr.net/gh/<owner>/<repo>@main/data/published/...）。
   仓库已本地 git init + 首次提交；推送需用户提供 GitHub 仓库。

4. [实测] 深度检测闭环价值：
   深度验证可用的节点（马来西亚 ss 118.107.222.231:65443，3 来源）
   客户端连接成功 → YouTube 返回 HTTP 200 → 系统代理接管生效。
   "深度检测 AVAILABLE" 与 "真实可用" 首次画上等号。

5. [新增] 目录源自动发现（type=index，借鉴 ghboost 的做法）：
   ghboost（github.com/lilyco-42/ghboost，MIT）把 lza6/free-VPN 的
   README 当"订阅源索引"动态提取订阅地址而非硬编码来源。
   NovaLink 吸收该思路：来源 Type=index 抓取目录文本后自动提取
   订阅 URL（跳过 blob 页/纯域名，去重限量 40 个），每个子 URL
   作为独立来源并发抓取、独立隔离。
   实测：lza6 目录展开后节点池 611 -> 1876（净增 654 个新节点），
   新节点深度检测后协议级可用从 1 个增至 25 个（较差 18 个）。
   注意：目录源中不少链接是 GitHub blob 页或已失效，失败隔离正常。
