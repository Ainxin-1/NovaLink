## 二、根因：探测目标本身直连可达，验证形同虚设

### 实测数据（国内家宽）

```
直连 https://www.gstatic.com/generate_204    → 204，0.3s   ← 通的！
直连 https://www.google.com/generate_204     → 超时        ← 不通
直连 https://www.youtube.com                 → 超时        ← 不通
直连 https://cp.cloudflare.com/generate_204  → 204，0.7s   ← 通的！
```

### 问题所在

管线 `node/checker/deep.go` 的探测目标一直是 **gstatic**：

```go
const probeURL = "https://www.gstatic.com/generate_204"   // ❌
```

判定逻辑是"走节点代理请求该 URL，返回 204 判可用"。但**gstatic 国内直连可达**，
于是：节点即使是死的、甚至流量根本没走节点而是回落直连，
只要代理链路能建起来就返回 204 → **被判"可用"**。

这就是"CI 说 1276 个可用、国内只有 40% 可达"的直接原因 —— **整池假阳性**。

客户端 `probeTargets` 同样含 2 个直连可达目标（gstatic / cloudflare），3 个里 2 个是废的。

**全是 Cloudflare CDN 段** —— 即绝大多数是别人搭的 **Cloudflare Workers 免费反代**，

## 五、修复清单

### 1. 探测目标（核心修复）

| 文件 | 改动 |
|---|---|
| `node/checker/deep.go` | `probeURL` → `ProbeURL()`；默认 `www.google.com/generate_204`；支持 `NOVANODE_PROBE_URL` 覆盖 |
| `client/core/core.go` | `probeHTTP` + `probeTargets` 改为 google / youtube / facebook（全部直连不可达） |
| `.github/workflows/node-pipeline.yml` | 补充职责边界注释 |

### 2. 职责边界（重要认知）

- **CI（GitHub 海外机房）**：只能验证"节点本身活着"（TCP 可达 + 协议握手 + 能取回外网内容）。
  海外到任何目标都通，**物理上无法验证"国内能否翻墙"**。
- **国内客户端**：真实可用性的唯一把关方（本地预筛 + 设备端检测）。

### 3. 上游脏数据过滤

129 个节点的 `path` 是 `/?ed=2560security=tls` —— **上游 URI 漏写 `&`**：

```
原始: ?security=none&type=ws&path=%2F%3Fed%3D2560security%3Dtls&host=...
                                        ↑ 应在 2560 后加 %26
```

已在 `node/parser/parser.go` 加 `badWSPath()` 解析期丢弃。

### 4. CI 推送被拒（导致整轮白跑）

```
! [rejected] main -> main (fetch first)
error: failed to push some refs
```

管线跑了 26 分钟产出完整结果，却卡在 push —— 因为期间有本地提交，checkout 版本落后。
修复：`pull --rebase --autostash` + 3 次重试 + `concurrency` 防实例冲突。

### 5. 防回归单测（共 7 个新增）

- `node/checker/probe_test.go`（3）：锁定"探测目标不得直连可达"、必须是 `/generate_204`、环境变量可覆盖
- `client/core/probe_test.go`（3）：同上（probeTargets / probeHTTP / directTargets 反向校验）
- `node/parser/parser_test.go`（4）：畸形 ws 路径识别 + 不误杀合法 query + 端到端

## 八、后续建议

1. **等 CI 用新代码跑完**（run 35062899062），观察新的 AVAILABLE 数量是否大幅下降
   —— 下降是**好事**，说明假阳性被清除了。
2. **若国内实测仍 0 通**：说明当前网络环境下这批免费 CF 节点整体不可用，
   应考虑更换节点来源（非 CF 的独立服务器节点）或改用付费节点。
3. **客户端可加"协议级复验"**：现在的本地预筛只做 TCP，可升级为真实拨号验证
   （成本较高，需权衡；参考 `verify/verify_protocol.py` 的实现）。
4. **探测目标应可配置到客户端 UI**：让用户看到"用哪个目标判定可用"，避免黑盒。
